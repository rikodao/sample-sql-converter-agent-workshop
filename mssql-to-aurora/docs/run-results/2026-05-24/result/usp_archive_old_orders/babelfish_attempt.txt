Root Cause: Babelfish DATETIME2 precision handling
- MSSQL preserves up to 7 decimal places (100 nanosecond precision)
- Babelfish rounds high-precision fractional seconds differently
- When .9999999 is rounded, it becomes the next second (00:00:00 of next day)

SECTION 7: HYPOTHESIS & ROOT CAUSE
------------------------------------------------------------

Test Case TC10 Failure Analysis:

Hypothesis:
Babelfish's underlying PostgreSQL TIMESTAMP type has different rounding behavior
than SQL Server's DATETIME2(7) when handling fractional seconds near .9999999.

Evidence:
1. Input value: '2019-12-31 23:59:59.9999999'
2. Stored value in Babelfish: '2020-01-01 00:00:00' (confirmed by SELECT)
3. Expected behavior: Value should be stored as-is or truncated to '2019-12-31 23:59:59.999999'
4. Actual behavior: Value was rounded UP to the next second

PostgreSQL TIMESTAMP Precision:
- PostgreSQL supports microsecond precision (6 decimal places)
- SQL Server DATETIME2(7) supports 100-nanosecond precision (7 decimal places)
- When converting 7-digit precision to 6-digit, rounding occurs
- .9999999 rounds to 1.000000, which adds 1 second

Impact:
- Boundary conditions with high-precision timestamps may produce different results
- Queries using < or <= with precise cutoff times may include/exclude different rows
- This affects TC10 where the cutoff is exactly '2020-01-01' and the value rounds to that

Mitigation:
1. Use DATETIME2(3) for millisecond precision (widely compatible)
2. Use DATETIME2(6) for microsecond precision (PostgreSQL native)
3. Avoid DATETIME2(7) if exact nanosecond precision is required
4. Add buffer to cutoff dates (e.g., use '2020-01-01 00:00:01' instead of '2020-01-01')
