CREATE PROCEDURE dbo.usp_dept_headcount_pivot
AS
BEGIN
    SET NOCOUNT ON;
    SELECT *
    FROM (
        SELECT
            d.name AS department_name,
            CASE WHEN e.is_active = 1 THEN 'Active' ELSE 'Inactive' END AS status,
            e.employee_id
        FROM dbo.departments d
        LEFT JOIN dbo.employees e ON d.department_id = e.department_id
    ) src
    PIVOT (
        COUNT(employee_id) FOR status IN ([Active], [Inactive])
    ) p
    ORDER BY department_name;
END

SECTION 4: BABELFISH LIMITATION ANALYSIS
============================================================================

Identified Issue: PIVOT Column Reference Resolution
Category: PARTIAL_SUPPORT - PIVOT Syntax Limitation

Description:
-----------
Babelfish supports PIVOT syntax at the DDL level (procedure creation succeeds),
but has a runtime limitation where column references from the source subquery
are not properly resolved after the PIVOT operation.

Specifically:
- The subquery 'src' contains: d.name AS department_name
- After PIVOT, the ORDER BY clause references: department_name
- Babelfish incorrectly tries to resolve 'd.name' instead of 'department_name'
- This suggests Babelfish's PIVOT implementation has issues with:
  * Column alias propagation from subquery to outer query
  * Scope resolution after PIVOT transformation

Known Babelfish PIVOT Limitations:
----------------------------------
1. ✓ Basic PIVOT syntax is supported (DDL creation works)
2. ✗ Complex column references in PIVOT subqueries may fail at runtime
3. ✗ Column alias resolution after PIVOT may be inconsistent
4. ✗ ORDER BY on pivoted columns may have scope issues
5. ? PIVOT with OUTPUT INTO clause (not tested in this case)

SECTION 7: HYPOTHESIS & ROOT CAUSE
============================================================================

Primary Hypothesis:
------------------
Babelfish's PIVOT implementation has a bug in column alias resolution where:
1. The parser accepts the PIVOT syntax during DDL creation
2. At runtime, the PIVOT operator fails to properly propagate column aliases
   from the source subquery to the outer query scope
3. The ORDER BY clause attempts to reference 'department_name' (the alias)
4. Babelfish incorrectly tries to resolve the original column 'd.name'
5. Since 'd' is not in scope after PIVOT, the error "column d.name does not exist" occurs

Supporting Evidence:
-------------------
1. DDL creation succeeds → Parser understands PIVOT syntax
2. Runtime execution fails → Execution engine has column resolution bug
3. Error mentions 'd.name' not 'department_name' → Alias not propagated
4. Same error in direct query → Not a procedure-specific issue
5. MSSQL executes successfully → Syntax is valid T-SQL

Alternative Hypotheses (Less Likely):
------------------------------------
1. ORDER BY clause issue: Unlikely, as the error mentions 'd.name' not 'department_name'
2. LEFT JOIN issue: Unlikely, as the error is specific to column resolution
3. CASE expression issue: Unlikely, as 'status' column is used in PIVOT, not ORDER BY
4. Subquery alias issue: Unlikely, as 'src' is properly defined

Conclusion:
----------
This is a known limitation of Babelfish's PIVOT implementation where column
alias resolution from subqueries is not correctly handled at runtime, despite
the syntax being accepted during DDL creation.
