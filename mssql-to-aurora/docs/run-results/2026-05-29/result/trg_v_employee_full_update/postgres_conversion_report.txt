## KEY TRANSFORMATIONS APPLIED
================================================================================

1. **Trigger Structure**
   - T-SQL: Single CREATE TRIGGER statement with inline logic
   - PG: Separate trigger function + CREATE TRIGGER statement
   - Reason: PostgreSQL requires trigger logic in a separate function

2. **Trigger Granularity**
   - T-SQL: Statement-level (implicit, uses inserted/deleted tables)
   - PG: Row-level (FOR EACH ROW, uses NEW/OLD records)
   - Reason: INSTEAD OF triggers on views typically operate per-row in PG

3. **Pseudo-tables vs Records**
   - T-SQL: `inserted` table with multiple rows
   - PG: `NEW` record (single row per trigger invocation)
   - Impact: JOIN pattern becomes direct field reference

4. **UPDATE Pattern**
   - T-SQL: `UPDATE e ... FROM employees e INNER JOIN inserted i ON ...`
   - PG: `UPDATE employees e SET ... WHERE e.employee_id = NEW.employee_id`
   - Reason: Row-level trigger processes one row at a time

5. **Return Value**
   - T-SQL: No explicit return
   - PG: `RETURN NEW;` required for trigger function
   - Reason: PostgreSQL trigger functions must return TRIGGER type

6. **SET NOCOUNT ON**
   - T-SQL: `SET NOCOUNT ON;` to suppress row count messages
   - PG: Removed (not needed, PG doesn't send row counts from triggers)

7. **Schema Mapping**
   - T-SQL: `dbo.employees`, `dbo.v_employee_full`
   - PG: `public.employees`, `public.v_employee_full`
   - Standard: dbo → public mapping

8. **Column Mapping**
   - All columns preserved: first_name, last_name, email, department_id, 
     salary, hire_date, is_active
   - No data type conversions needed (assuming compatible base types)

✓ Both prevent default view update behavior (INSTEAD OF)

### Execution Model Differences:

1. **Multi-row Updates**
   - T-SQL: Single trigger execution for statement, processes all rows via JOIN
   - PG: Trigger function called once per row being updated
   - Impact: Performance characteristics differ, but result is equivalent

2. **Transaction Scope**
   - T-SQL: Trigger executes in same transaction as triggering statement
   - PG: Same behavior (trigger is part of triggering statement's transaction)
   - Impact: None (equivalent)

3. **Error Handling**
   - T-SQL: Error in trigger rolls back entire statement
   - PG: Error in trigger function rolls back entire statement
   - Impact: None (equivalent)

4. **@@ROWCOUNT**
   - T-SQL: @@ROWCOUNT after view update reflects rows in inserted table
   - PG: GET DIAGNOSTICS ROW_COUNT reflects actual rows updated in base table
   - Impact: Minor (may differ if some rows don't match in base table)

### Edge Cases:

1. **No Matching Row in Base Table**
   - T-SQL: UPDATE with JOIN silently skips non-matching rows
   - PG: UPDATE with WHERE silently skips non-matching rows
   - Result: Equivalent behavior

2. **NULL Values**
   - T-SQL: NULL values in inserted table are written to base table
   - PG: NULL values in NEW record are written to base table
   - Result: Equivalent behavior

3. **Concurrent Updates**
   - Both: Subject to transaction isolation level of session
   - Both: May encounter locking or serialization conflicts
   - Result: Equivalent behavior (depends on isolation level)

## KNOWN LIMITATIONS & CONSIDERATIONS
================================================================================

1. **Performance Characteristics**
   - Row-level triggers in PG are called once per row
   - For bulk updates (1000s of rows), this may be slower than T-SQL's 
     statement-level approach with set-based JOIN
   - Consider statement-level trigger with transition tables for high-volume scenarios

2. **Transition Tables Alternative**
   - PostgreSQL 10+ supports transition tables (NEW TABLE, OLD TABLE)
   - Could convert to statement-level trigger for closer T-SQL equivalence:
   ```sql
   CREATE TRIGGER trg INSTEAD OF UPDATE ON view
   REFERENCING NEW TABLE AS new_table OLD TABLE AS old_table
   FOR EACH STATEMENT EXECUTE FUNCTION trg_fn();
   ```
   - Would require rewriting function to use new_table instead of NEW

3. **Department Columns**
   - Source comment mentions view may include department columns
   - Current trigger only updates employees table
   - If view includes department.department_name, updates to that column 
     would be silently ignored (as intended for read-only reference data)

4. **Error Messages**
   - T-SQL custom error messages (RAISERROR) would need conversion to RAISE EXCEPTION
   - Current implementation has no explicit error handling
   - Consider adding validation logic if source trigger had it

5. **Audit/Logging**
   - If source trigger included audit logging, that logic needs to be added
   - PG trigger functions can insert into audit tables just like T-SQL
