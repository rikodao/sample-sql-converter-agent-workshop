CONVERSION APPROACH
================================================================================

T-SQL AFTER Trigger → PostgreSQL Trigger Function + Trigger

Key Transformations:
--------------------

1. Trigger Structure:
   T-SQL: CREATE TRIGGER ... AS BEGIN ... END
   PG:    CREATE FUNCTION ... RETURNS trigger + CREATE TRIGGER ... EXECUTE FUNCTION

2. Pseudo-Tables → Record Variables:
   T-SQL: inserted / deleted (set-based, multi-row)
   PG:    NEW / OLD (row-based, FOR EACH ROW)
   
   Note: PostgreSQL processes multi-row operations by invoking the trigger
   function once per row, so the behavior is equivalent.

3. Operation Type Detection:
   T-SQL: IF EXISTS (SELECT * FROM inserted) AND EXISTS (SELECT * FROM deleted)
   PG:    TG_OP variable ('INSERT', 'UPDATE', 'DELETE')

4. System Functions:
   - SYSTEM_USER → session_user
   - GETDATE() → current_timestamp
   - NEWID() → gen_random_uuid()

5. Control Flow:
   T-SQL: IF ... BEGIN ... END
   PG:    IF ... THEN ... END IF;

6. Return Values:
   - AFTER triggers in PostgreSQL must return NEW (for INSERT/UPDATE) or OLD (for DELETE)
   - T-SQL triggers don't have explicit return values

DETAILED CONVERSION MAPPING

Original T-SQL Pattern:
-----------------------
CREATE TRIGGER dbo.trg_audit_employees
ON dbo.employees
AFTER INSERT, UPDATE, DELETE
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @operation_type VARCHAR(10);
    ...
    IF EXISTS (SELECT * FROM inserted) AND EXISTS (SELECT * FROM deleted)
        SET @operation_type = 'UPDATE';
    ...
    INSERT INTO dbo.employee_audit (...) SELECT ... FROM inserted i;
END;

Converted PostgreSQL Pattern:
------------------------------
CREATE FUNCTION public.trg_audit_employees_func()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
    v_operation_type VARCHAR(10);
    ...
BEGIN
    v_operation_type := TG_OP;
    ...
    IF TG_OP = 'INSERT' THEN
        INSERT INTO public.employee_audit (...) VALUES (..., NEW.column, ...);
        RETURN NEW;
    END IF;
    ...
END;
$$;

CREATE TRIGGER trg_audit_employees
AFTER INSERT OR UPDATE OR DELETE
ON public.employees
FOR EACH ROW
EXECUTE FUNCTION public.trg_audit_employees_func();

COMPATIBILITY NOTES
================================================================================

PostgreSQL vs SQL Server Trigger Differences:
----------------------------------------------

1. Execution Model:
   - SQL Server: Set-based (inserted/deleted tables contain all affected rows)
   - PostgreSQL: Row-based (NEW/OLD contain single row, trigger fires per row)
   - Impact: Functionally equivalent, but PostgreSQL may be slower for bulk operations

2. Transaction Context:
   - SQL Server: Trigger runs in same transaction as triggering statement
   - PostgreSQL: Same behavior (trigger runs in same transaction)
   - Impact: None (both support rollback)

3. Nested Triggers:
   - SQL Server: Controlled by nested triggers option
   - PostgreSQL: Supported by default
   - Impact: If employee_audit has triggers, they will fire in PostgreSQL

4. Recursive Triggers:
   - SQL Server: Controlled by recursive triggers option
   - PostgreSQL: Prevented by default (trigger won't fire on its own table)
   - Impact: None for this trigger (doesn't modify employees table)

5. INSTEAD OF Triggers:
   - SQL Server: Supported on tables and views
   - PostgreSQL: Supported on views only (tables use BEFORE triggers)
   - Impact: None (this is an AFTER trigger)

6. Error Handling:
   - SQL Server: Can use TRY...CATCH in trigger
   - PostgreSQL: Can use EXCEPTION block in trigger function
   - Impact: None (this trigger doesn't have error handling)

================================================================================
PERFORMANCE CONSIDERATIONS
================================================================================

1. Row-by-Row Execution:
   - PostgreSQL triggers fire once per row
   - For bulk operations (1000+ rows), this may be slower than SQL Server's set-based approach
   - Mitigation: Consider statement-level triggers if performance is critical

2. UUID Generation:
   - gen_random_uuid() is fast but not as fast as sequential IDs
   - Impact: Minimal for typical audit logging scenarios

3. Timestamp Precision:
   - PostgreSQL timestamp has microsecond precision
   - May result in slightly larger storage than SQL Server's millisecond precision
   - Impact: Negligible

4. Indexing:
   - Consider adding indexes to employee_audit table:
     - CREATE INDEX idx_employee_audit_employee_id ON public.employee_audit(employee_id);
     - CREATE INDEX idx_employee_audit_operation_date ON public.employee_audit(operation_date);
     - CREATE INDEX idx_employee_audit_operation_type ON public.employee_audit(operation_type);
