Changes:

- ERROR_SEVERITY(), ERROR_STATE() → Not available in PostgreSQL

Limitations:
- PostgreSQL does not have direct equivalents for ERROR_SEVERITY() and ERROR_STATE()
- Error numbers (SQLSTATE) are different from SQL Server error numbers
- Result set return from exception handler converted to RAISE NOTICE

4.3 BEHAVIORAL DIFFERENCES
---------------------------

Known Differences:
1. Result Set Return:
   - T-SQL: Returns result set with SELECT
   - PL/pgSQL: Uses RAISE NOTICE + INOUT parameters
   - Impact: Calling code must be adapted
   - Mitigation: Use INOUT parameters for all return values

2. Error Information:
   - T-SQL: ERROR_NUMBER(), ERROR_SEVERITY(), ERROR_STATE()
   - PL/pgSQL: RETURNED_SQLSTATE only
   - Impact: Less detailed error information
   - Mitigation: SQLSTATE and SQLERRM provide sufficient info for most cases

3. DATETIME Precision:
   - T-SQL: GETDATE() returns DATETIME (millisecond precision)
   - PL/pgSQL: CURRENT_TIMESTAMP returns TIMESTAMP (microsecond precision)
   - Impact: created_date/modified_date have higher precision
   - Mitigation: None needed (higher precision is acceptable)

4. String Length Function:
   - T-SQL: LEN() ignores trailing spaces
   - PL/pgSQL: LENGTH() counts trailing spaces
   - Impact: None (we use RTRIM before LENGTH)
   - Mitigation: Already handled in conversion

5. Collation:
   - T-SQL: Default case-insensitive (depends on collation)
   - PL/pgSQL: Default case-sensitive
   - Impact: None (we use LOWER() for case-insensitive comparison)
   - Mitigation: Already handled with LOWER()

Equivalent Behavior:
- NULL handling: Same
- String trimming: Same (LTRIM, RTRIM)
- Case-insensitive comparison: Same (using LOWER())
- Transaction rollback: Same
- Parameter passing: Same (OUTPUT → INOUT)
- RETURN statement: Same (exits procedure)

SECTION 8: ALTERNATIVE IMPLEMENTATION - FUNCTION
============================================================================

If INOUT parameters are problematic with your database driver, consider
converting to a function returning a composite type:

```sql
CREATE TYPE public.dept_creation_result AS (
    department_id INT,
    validation_status VARCHAR(50),
    error_message VARCHAR(500)
);

CREATE OR REPLACE FUNCTION public.usp_validate_and_create_dept_fn(
    p_department_name VARCHAR(100),
    p_location VARCHAR(100) DEFAULT NULL,
    p_manager_id INT DEFAULT NULL,
    p_min_name_length INT DEFAULT 3,
    p_max_name_length INT DEFAULT 100
)
RETURNS public.dept_creation_result
LANGUAGE plpgsql
AS $$
DECLARE
    v_result public.dept_creation_result;
    -- ... other variables
BEGIN
    -- ... same logic as procedure
    
    -- Instead of setting INOUT parameters:
    v_result.department_id := p_new_department_id;
    v_result.validation_status := p_validation_status;
    v_result.error_message := p_error_message;
    
    RETURN v_result;
END;
$$;
```

Calling code:
```sql

    'Engineering', 'Building A', 101, 3, 100
);
```

Note: Functions cannot use COMMIT/ROLLBACK, so transaction control
would need to be handled by the caller.
